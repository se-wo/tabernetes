### Items

1. **The broker** (`web/src/memory.js`). One broker in the page. It counts the Wasm memories of the page, of all node workers and of all their pod workers and transpile workers, with the numbers of section 14:
   - the Go binary of the page 2, of each node worker 1;
   - a transpile worker 1, after its first component;
   - a command component 1, a module 2;
   - a proxy container 1 (the instance of the link check, until garbage collection), and 1 for each active instance;
   - the memory of an instance that ended, until the garbage collection of its pod worker.

   **Design gap:** the browser has no interface that gives the limit (approximately 125 in Chromium, section 14; Firefox and Safari not examined). Smallest decision: the constant 125 of section 14, and the broker learns a smaller limit when the browser refuses a memory while the count is lower. Write it into 8.6.

   **Design gap:** the plan does not say how the containers share the limit. Smallest decision that adds no new failure:
   - A start never waits for the broker: a pod worker of a command component, a module, a node worker and the first instance of a proxy container start as now. They fail as section 8.6 says if the browser refuses the memory.
   - The instances 2 to 16 of a proxy container (PX9) ask the broker. It gives a grant while the free memories are more than a reserve for starts (for example 8). Else the request waits in the queue of PX10 and PX34, with the lines of PX34.
   - The broker serves the waiting containers in sequence (FIFO over all containers), so one container cannot take all memories.
   - A wait for a grant has a limit of a few seconds (for example 2 seconds). After it, the pod worker tries to instantiate without a grant, and PX34 handles a failure. So a broker that counts too high never stops a container.
   - If this is less code: count only live memories (no grants), and use the count only to send `collect` (item 3). Use the smaller of the two decisions.
   - The broker must not make PX8 and PX9 slower: with free memories, a request does not wait for a message round trip before its instance, or the wait is less than 1 ms. Run the full e2e suite, and compare the times of the PX8 to PX10 tests (`wasi-proxy.test.mjs`) before and after your change. Put the numbers into the PR.
   - The end of a pod worker (`end` in `newPodWorkers`, and `exit` of a module) frees all its memories and grants.

   **Design gap:** the memories of ended instances. Examine a `FinalizationRegistry` in the pod worker for the instances (or their memories): the pod worker then reports a memory as free only after the garbage collection. Record whether Chrome calls it in time.

   **Design gap:** decision 14 says that the Go side examines each message of a pod worker. The broker messages do not go to the Go side. The broker examines them (the `KINDS` of `wasi_messages.js`) and trusts no number of a pod worker: a pod worker can have at most `MAX_INSTANCES` grants.
2. **Messages** (plan rule 4).
