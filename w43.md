## Facts at your start (from the parent)

**W4.1 API.** It is on the branch `wasi/w4.1-udp-base`, commit f15ffccf67131e1d19fc10d91c7062f2896d7648. Its PR follows soon. Start from that branch. Rebase onto main when W4.1 has merged. The signatures are exactly as in your brief, fully implemented, with unit tests in `tabnode_udp_test.go`.

The path of a datagram in `(*udpConn).WriteTo` and `Write`:

1. A datagram of more than 65,507 bytes gives `errDatagramTooLarge` (EMSGSIZE). This check comes before the pending error.
2. Then the closed state, a past write deadline and the pending error.
3. A dst in 127.0.0.0/8 becomes the socket's IP.
4. `udpRoute(c.ctx, src, dst)` returns `from` and `to`, or `udpRefuse` (refused at once) or `udpDrop`. It is called without a lock of the table, and it must not wait. A test can swap it (`udpHook`).
5. If no socket has `to` and the IP is a pod IP of this tab node or `tabNodeIP`, the datagram is refused (UD8). For any other IP, it is dropped (phase 5). If the receiver has a "udp" loopback row and the real `src` IP is not the receiver's IP, it is refused (UD21).
6. In `deliver`, a connected receiver drops a datagram when `from != remote`. A full queue (256 KiB of payload) drops the datagram.

The pending error:

- A refusal sets it. One of ReadFrom, Read, WriteTo or Write takes it, whichever comes first.
- The call returns an error that wraps `syscall.ECONNREFUSED` (n=0). A write that takes it sends nothing.
- Unconnected sockets never get it.
- The constants `udpPendingOnRead`, `udpPendingOnWrite`, `udpPendingWriteSends` and `udpRefuseUnconnected` hold the runwasi points.

Other parts of the API:

- `Connect(netip.AddrPort{})` and `Connect(0.0.0.0:0)` both remove the remote address.
- `Write` without a remote address gives EDESTADDRREQ.
- `listenPodUDP` errors wrap `errPortInUse` (binds are exclusive) or `EADDRNOTAVAIL`. Port 0 uses `claimFreePort(proto, ip)` in `tabnode_dial.go`.
- `ReadFrom` gives the real table IPs. The pod worker maps the pod IP to 127.0.0.1 for loopback sockets.
- `Close` and the end of ctx remove the socket, its port and its loopback row.
- AC1: WriteTo charges its time to `procOf(ctx).c`. Callers do not charge it again.

**runwasi facts from W4.5a, part 1** (wasmtime 36.0.10 on Linux; the Docker run can still correct them):

- **Rule 7, DECISION:** only the NEXT SEND of a CONNECTED socket gets `connection-refused`, ONE time, and that send does not send its datagram.
  - `receive` never gets it. Unconnected sockets never get it. Two refusals before any call give one error.
  - The Go side emits exactly one `error` message for it. The worker keeps it and gives it to the next send. W4.4b corrects the text of rule 7.
- **Binds:**
  - 0.0.0.0:P twice gives `address-in-use`. 127.0.0.1:P and 0.0.0.0:P conflict in both orders.
  - On Linux, pod-IP:P and 127.0.0.1:P bind together. The tab gives `address-in-use`; this is the accepted section 11 row.
  - UDP and TCP on the same port is ok (UD1).
  - Port 0 gives a port in 32768..60999.
- **Size:** 65,508 bytes gives `datagram-too-large`. The worker refuses it before Go.
- **Rule 4:**
  - Broadcast 255.255.255.255 gives `access-denied`. Multicast is ok; the tab drops it.
  - A connected socket that sends to another address gives `invalid-argument`. The worker checks this.
- **Options:**
  - UDP buffer sizes default to 106496. Set 1 reads 1152 (receive) or 2304 (send).
  - The unicast hop limit is 64.
- **Same pod:** a 0.0.0.0 client sends to 127.0.0.1:P. On Linux the answer comes from 127.0.0.1:P; the tab gives the pod IP (section 11).
- **Queue on loopback:** with 1000 datagrams of 1024 bytes and a read after 3 s, Linux received 92. The tab keeps 256 KiB of payload (section 11).
